## Unreleased: Item names, icons and instance stats per loot

A loot item now shows the name and icon it was reported with. Earlier, a later
loot of an item with equal stats reused the first stored name and icon, so a
Polish loot could show an English name, and an icon change was lost.

- Loot item `stat` includes that loot's own `created`, `gold`, `amount` and
  `opis` values. Earlier it repeated the values of the first loot stored with
  the same stats. Loot items accepted before this change keep their stored
  `stat`.
- Item search can return several hits with the same `id`: one per game version
  and name, such as a Polish and an English name of one item. Deduplicate by
  `id` and `name` rather than by `id` alone.
- `POST /loots` is unchanged. Send `name`, `icon` and `stat` exactly as the game
  shows them; do not translate them.

## Unreleased: Margonem game version on loots and NPC search

Margonem runs a Polish edition on `*.margonem.pl` and an international edition
on `*.margonem.com`. The same template or item id can mean different things in
each edition, and a world name does not identify the edition.

- `POST /loots` accepts an optional nullable `gameVersion`: `pl` or `en`.
  Derive it from the game page's hostname: the edition domain or any
  subdomain of it. Send `null`, or omit the field, when the host is not a
  recognized edition domain; never default to `pl`. The API validates the value
  but cannot verify where the client ran, so do not treat it as proof of
  anything else.
- Retrying a loot, or submitting one another client already reported, keeps the
  game version it was first accepted with.
- NPC search hits add a nullable `gameVersion`. Equal ids with different game
  versions are different NPCs. Hits from older clients and from existing data
  have `null`; do not assume an edition for them.

Deploy the database migration, the search service, the API and the game client
in that order. Older clients keep working and their loots stay unknown.

## Unreleased: Timer NPC search follows timer visibility

`GET /guilds/{guildId}/timers/npcs/search` now applies the same visibility as
the timer list. Timers whose NPC type or level is outside the caller's roles
are omitted before `limit` is applied, so they no longer reveal an NPC's
identity, location or respawn configuration.

- `world` is optional. Without it, the search covers every world of the
  Organization, and each result adds `world`.
- `search` is optional when `npcIds` or `templateIds` is present. Both accept
  repeated positive integers: `npcIds` matches a timer's runtime NPC id and
  `templateIds` matches its template id. A request needs at least one of
  `search`, `npcIds` or `templateIds`; otherwise it returns `400`.
- Manual timers remain excluded.

Existing callers that send `search` and `world` keep their behavior, except
that hidden timers no longer appear. Generated clients include the new
parameters and field for the next SDK release.

## Unreleased: Explicit NPC runtime and template identities

Margonem gives every NPC spawn a runtime id (`npc.id`, the battle
`originalId`) and every monster template a template id (`npc.tpl`). Several
spawns share one template.

- `POST /loots` accepts optional `npcs[].runtimeId` and nullable
  `npcs[].templateId`. When either is present, `npcs[].id` is ignored for
  identity; keep sending it for older API revisions. Send `templateId: null`
  when the template is unknown; never substitute the runtime id.
- `POST /timers/auto` accepts optional nullable `npc.templateId`. `npc.id`
  remains the runtime id and still identifies the timer, so spawns sharing a
  template keep separate timers.
- Timer responses, timer history and `GET /guilds/{guildId}/timers/npcs/search`
  add `templateId`, which is null until a client reports it. A later
  submission without it keeps the stored value.
- Notification rules accept `npcTemplateIds`, at most five together with
  `npcId` and `npcIds`. A template id matches every timer observed with that
  template; `npcId` and `npcIds` still match a timer's own id.
- Search NPC hits add `identityNamespace`: `template`, `runtime` (a spawn
  observed without a template) or `legacy` (an overloaded id from an older
  client). Equal ids in different namespaces are different NPCs.

Deploy the database migration, the search service, the API, the web app and
the game client in that order. Older clients keep working and write `legacy`
identities. Existing saved filters and legacy records are not remapped.

## Unreleased: Conditional party observations

`POST /messaging/party-gathering/{notificationId}/party-observation` accepts
an optional positive integer `expectedRevision`. Use the latest room projection's
`revision` to prevent a delayed observation from overwriting a newer roster.
When supplied, a stale revision or a concurrent write returns
`409 REVISION_CONFLICT`. A successful conditional observation advances the room
revision even if the roster is unchanged and was observed moments ago. Requests
without the field keep their existing behavior, including returning the current
room without a new revision for an unchanged roster observed within 45 seconds.

After a conflict or an uncertain HTTP result, read the room again and retry the
latest roster with its current revision. Bound both the requests and retry count;
aborting HTTP does not cancel a server write. Deploy the API to every writer
before relying on the precondition. No persistence migration is required.
Generated clients include the optional field for the next SDK release.

## Unreleased: Event hero lists keep history

`PATCH /guilds/{guildId}/events/{eventId}` no longer rebuilds the event's heroes
and maps when the request includes `heroNpcs`. Heroes are matched by `npcName`
and maps by `mapId`, so retained heroes and maps keep their IDs, kills, kill
points, tracking history and ranking entries. The list can add heroes, add
maps, rename maps and set a hero's `npcId`; omitting `npcId` keeps the stored
value.
As with the map create operation, a map added to an existing hero starts with
an open unassigned coverage gap.

A `heroNpcs` list that omits an existing hero or map now returns `400` and
changes nothing. Previously the omitted records were deleted with their history.
Repeated hero names, or a repeated `mapId` within one hero, also return `400`.
Remove a hero with `DELETE /guilds/{guildId}/events/{eventId}/heroes/{heroId}`
and a map with
`DELETE /guilds/{guildId}/events/{eventId}/heroes/{heroId}/maps/{mapId}`.

Deleting a hero removes its maps, kills, kill points and tracking history, and
now also its ranking entries, so event ranking totals match the remaining kill
points. No migration is required.

## Unreleased: Event kill history

`GET /guilds/{guildId}/events/{eventId}/kill-history` adds a paginated summary
of kills visible to the caller. It requires `LOOTLOG_EVENTS_READ` and supports
read-only API keys within their Organization scope. Optional query parameters
are `heroId`, `memberId`, `cursor` and `limit`. The limit is an integer from 1
to 100 and defaults to 20.

The response contains `kind`, `data` and `nextCursor`. `kind` is `event` unless
`memberId` is supplied, when it is `member`. Summaries include hero identity,
timestamps, manual closure status and `participantCount`. This count includes
all saved participant point records, including participants with
`wasPresent: false`. Member summaries also include the selected member and
their scoring and tracking data. Lists omit map presence, roles and other
participants' full records. Existing detail and timeline endpoints remain
available.

Treat the new cursor as opaque and pass it unchanged with the same Organization,
event and filters. Results use `killedAt DESC, id DESC`; the cursor remains usable
if its boundary kill is deleted. Invalid cursors, mismatched filters and invalid
limits return `400`. Each request applies current access rules. Pagination does
not freeze a snapshot of the history.

The existing event, hero and member kill-list endpoints are deprecated. Their
response shapes and UUID cursors remain supported with corrected chronological
pagination. A missing, hidden or out-of-scope UUID cursor returns the same
`400 Invalid cursor` response. Inaccessible resources return `404`.

Apply the database index migration and deploy the API before migrating clients
to the new endpoint. The migration changes indexes only. Generated clients
include the endpoint for the next SDK release; SDK publication remains a
separate release step.

## Unreleased — Realtime latency probe

The realtime v1 `session.joined` event and `session.join` response add an
optional `capabilities` list. Gateways that list `connection.ping` accept the
`connection.ping` command and answer it without side effects, including on
integration connections. The SDK realtime client adds `probeLatency()`, which
reports through `subscribeHeartbeatLatency`.

Deploy the gateway before relying on the probe. Clients send the command only
when the capability is listed, so clients connected to older gateways keep the
heartbeat measurement. No migration is required.

## Unreleased — Notification schedules and role level ranges

Notification rule create and update requests accept `scheduledUntil: null`.
For a recurring rule, `null` removes the end date; omitting the field preserves
it. Switching to a one-time schedule clears recurring fields, including the end date.
Send only fields relevant to the selected schedule type. For daily and weekly
schedules, omit `scheduledAt` to calculate the next occurrence from the selected
time, weekday and timezone when the schedule changes.

Role update requests reject `lvlRangeFrom` and `lvlRangeTo` values that are not
integers from 0 to 500, and ranges where `lvlRangeTo` is lower than
`lvlRangeFrom`, with `400 Bad Request`. A role saved earlier with a reversed range
must receive a corrected range on its next update.

Deploy the API before clients begin sending `null`. Existing valid requests remain
compatible, and no database migration is required. Generated SDK types include
these changes for the next SDK release.

## 2026-09-17 — SDK 0.1.1

Documentation update with runnable organization, timer and loot examples,
filtering, cursor pagination and error handling. No runtime or API contract
changes; no migration is required.

## 2026-09-17 — SDK 0.1.0

First npm release of [`@lootlog/sdk`](https://www.npmjs.com/package/@lootlog/sdk/v/0.1.0):

- Typed HTTP functions for the main, activity, battlelog and search APIs.
- A shared realtime client for server-side integrations.
- Public OpenAPI JSON exports and bundled TypeScript declarations.

Install with `npm install @lootlog/sdk` or `bun add @lootlog/sdk`. See the
[SDK guide](/docs/sdk) for configuration and usage. This package release does
not change the game client API version or introduce new HTTP endpoints.

## Portal baseline

Documentation for the public game client API v1, an HTTP reference in Scalar, personal API keys, and an SDK for server integrations. The development environment supports verification before production releases.

The public game client object retains `apiVersion: 1`. Published contract changes will be documented here with migration instructions. Check the reference generated from service schemas for current HTTP operation parameters.
