title: Realtime
description: Subscribe to Organization events over WebSocket and keep HTTP for reads and writes.

The realtime gateway pushes changes, such as a new timer or loot, to your
server as they happen. Read the initial state and perform writes over HTTP; use
realtime to keep it current.

## Connect

Server integrations send `X-Api-Key` in the WebSocket handshake. Browsers do not
let a page set this header, so realtime with a key works only from a server.
Userscripts use the [game client API](/docs/game-client) and need no connection
of their own.

| Environment | Gateway                        |
| ----------- | ------------------------------ |
| Development | `wss://dev-gateway.lootlog.pl` |
| Production  | `wss://gateway.lootlog.pl`     |

The [TypeScript SDK](/docs/sdk) provides `RealtimeClient`, which speaks the
protocol and accepts a server-side WebSocket implementation.

Frames are JSON text. A client of your own offers the
`lootlog.realtime.json.v1` subprotocol and sends each command as a text frame.

## Bun example

Run this example on a server using Bun. In a TypeScript project, use Bun types and the `ES2022` or `ESNext` library without `DOM` so the WebSocket constructor accepts server options. Set `LOOTLOG_API_KEY` and `LOOTLOG_ORGANIZATION_ID` for the development environment. The WebSocket factory adds the key header; do not pass it in the URL.

```ts
import { RealtimeClient } from "@lootlog/sdk/realtime";

const apiKey = process.env.LOOTLOG_API_KEY;
const organizationId = process.env.LOOTLOG_ORGANIZATION_ID;
if (!apiKey || !organizationId)
  throw new Error("Missing Lootlog configuration");

const client = new RealtimeClient({
  url: "wss://dev-gateway.lootlog.pl",
  webSocketFactory: (url, protocols) =>
    new WebSocket(url, {
      protocols,
      headers: { "X-Api-Key": apiKey },
    }),
});
const stopEvents = client.subscribe((event) => {
  if (event.type === "timer.created") console.log(event.data);
});
const stopState = client.subscribeState((state) => console.log(state));

// Store the session and subscription before connecting so they can be restored.
await client.join({});
await client.subscribeScope({
  topic: "organization.timers",
  organizationId,
  world: "fobos",
});
client.connect();

process.once("SIGINT", () => {
  stopEvents();
  stopState();
  client.disconnect();
});
```

The `ready` state means the client has joined the session. The SDK restores the
stored session and subscriptions after reconnecting. Events carry changes, not
the current state: fetch the initial timer list [over HTTP](/docs/http) first.
After a persistent authentication error, stop retrying and alert whoever runs
the integration.

## Topics and events

Subscribe to a topic for one Organization with `subscribeScope`. Each topic
needs the matching read permission in that Organization.

| Topic                        | Needs permission to read | Events                                                                                     |
| ---------------------------- | ------------------------ | ------------------------------------------------------------------------------------------ |
| `organization.timers`        | Timers                   | `timer.created` (also sent when a timer changes), `timer.deleted`, `hero-sighting.updated` |
| `organization.loots`         | Loot                     | `loot.created`, `loot.share-updated`                                                       |
| `organization.chat`          | Chat                     | `chat.created`, `chat.updated`, `chat.deleted`, `chat.cleared`                             |
| `organization.reservations`  | Reservations             | `reservation.created`, `reservation.changed`, `reservation.deleted`                        |
| `organization.notifications` | Notifications            | `notification.sent`, `party-gathering.updated`, `party-gathering.cancelled`                |
| `organization.presence`      | Online players           | `presence.snapshot`, `presence.delta`                                                      |
| `organization.members`       | Administration           | `member-refresh.updated`                                                                   |

`ServerEvent` in `@lootlog/sdk/realtime` types every event and its payload.

## Allowed actions

An integration receives available events and uses permitted subscriptions and queries. Its scope is limited by the key's Organizations and the user's current permissions. Perform writes, such as adding a timer, over HTTP.

An integration connection does not represent a character's presence in the game. The game client publishes presence and game observations.

## Presence snapshots

`presence.fetch` takes an Organization ID, an optional world and an optional
`delivery: "response"`. With a `requestId` and that option, the snapshot arrives
only in the correlated response. Without the option, the gateway also emits a
`presence.snapshot` event, and a command without a `requestId` always receives
that event.

With response delivery, start from the response and apply `presence.delta`
events for later changes. Permission and location filters apply to both
delivery modes.

## Connection latency

`session.joined` and the `session.join` response list the gateway's
`capabilities`. When the list contains `connection.ping`, the gateway answers a
`connection.ping` command at once with an empty `data` object, without touching
presence or other state. Send it only when the capability is listed: a gateway
closes the connection on a command it does not know.

The SDK's `probeLatency()` sends one ping when the gateway supports it and the
client is `ready`, and reports the round trip through
`subscribeHeartbeatLatency`. Without the capability, that subscription keeps
reporting the presence heartbeat, which runs every 25 seconds. Probe only while
the latency is on screen instead of on a fixed fast interval.

## Reconnect

Mark data as stale when the connection is lost. The SDK restores subscriptions after reconnecting; fetch the current state over HTTP at that point. Do not assume you will receive every event from the outage.

A busy gateway rejects `session.join` with a retryable error that carries
`retryAfterMs`. Wait at least that long before you reconnect or join again. The
SDK applies this delay to its next reconnect.

If you register `setReconnectHandler`, it replaces the default session restore.
The handler still runs when a synchronous connection-state observer starts a
join. Coordinate these callbacks so one owns the join, and use the handler for
any additional recovery work. Without a custom handler, a synchronous observer's
join suppresses the default join to avoid duplicate startup requests.

Authorization must be renewed at least every 60 seconds. Deleting the key, losing access, or failing to renew blocks further communication. Do not retry indefinitely when a connection is rejected because of an invalid key.
