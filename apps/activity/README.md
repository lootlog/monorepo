# Activity service

The service owns Organization activity logs and private confirmed game online history. The histories have separate persistence and retention policies. Neither the Organization log permissions nor member removal grant access to, or delete, private account-wide history.

## Online history contract

`GET /users/@me/activity/online?from=YYYY-MM-DD&to=YYYY-MM-DD` accepts an inclusive range of 1–112 valid calendar dates. The edge's authenticated `x-auth-user-id` determines the internal User. There is no request parameter for selecting another User, Discord identity, Organization or world. Keep this service behind the existing forward-auth boundary; do not expose a bypass accepting client-provided identity headers.

The response contains `timezone: Europe/Warsaw`, `trackingStartedAt`, `lastObservedAt`, `status` and daily `onlineSeconds`. `trackingStartedAt` is the earliest healthy global collector watermark, establishing when instrumentation began; `lastObservedAt` is the latest observation for this User, not their collector's heartbeat. Days before tracking, expired days, and future days contain null, not fabricated zeroes. Each day also exposes `partial`: instrumentation start, today, and the retention cutoff may cover only part of a day. A partially observed first day returns confirmed seconds when positive, otherwise null. Once global tracking starts, Users without game sessions have zero on fully covered days. No historical backfill is inferred from connect/disconnect activity logs.

Cumulative checkpoints use the existing signed Rabbit event envelope on `users.online.checkpoint.v1`. A checkpoint includes internal `userId`, `sessionId`, `segmentId`, immutable source `startedAt`, confirmed `endedAt`, and `observedAt`; all instants carry a UTC offset. `version: 1` and `type: checkpoint` identify the contract. A disconnected gap starts another segment. AFK game sessions count; web-only sessions do not. Parallel sessions, worlds and Organizations are unioned for the User before splitting at Warsaw calendar midnights. DST days can contain 23 or 25 hours.

The same route also carries `type: collector`, `version: 1`, `observedAt` and `status: healthy | degraded`. A healthy collector watermark no older than 180 seconds yields `fresh`, including for offline Users. A missing, old or degraded watermark yields `stale`; no global tracking metadata yields `unavailable`. A degraded observation also persists a 180-second lease; healthy messages from another Gateway cannot clear that lease, including after Activity restarts. Older health observations cannot replace newer state, and a healthy duplicate cannot replace a degraded observation at the same instant.

The durable consumer acknowledges checkpoints after database commit. The queue uses RabbitMQ single-active-consumer mode with prefetch one; a database failure keeps the delivery unacknowledged and retries every five seconds, so later collector watermarks cannot overtake unpersisted checkpoints. Other activity queues remain independent. The primary key `(userId, sessionId, segmentId)` and maximum end/observation make redelivery and out-of-order delivery idempotent. Stored starts are clipped to the retention cutoff, and incoming and stored starts are compared after the same clipping. This forgets expired timestamps without rejecting valid old cumulative checkpoints or reviving their expired portions. Starts that differ inside the retained window remain invalid. Invalid JSON, schemas or signatures are published to the durable `.dlq` and acknowledged only after publication succeeds. The service does not consume or discard that DLQ. Transient database failures have no finite attempt budget; shutdown requeues the unacknowledged delivery. The durable retry queue remains the fallback for delivery failures outside ingestion. Inspect and replay retained DLQ records only after resolving their cause; never log private payloads.

## Migration and rollout

1. Deploy migrations `drizzle/migrations/0001_user_online_history.sql` and `drizzle/migrations/0002_online_history_16_week_retention.sql` using `bun run --cwd apps/activity db:migrate:deploy` in the approved deployment environment. The existing migration command first verifies the legacy activity schema, then installs the independent online tables and indexes idempotently. The second migration physically deletes expired online history and trims crossing intervals; this retention reduction is irreversible. Existing seven-day Timescale activity retention remains unchanged.
2. Deploy Activity with the new durable queue and consumer before enabling the Gateway producer. Both services must use the existing `ACTIVITY_EVENT_SIGNATURE_SECRET` and Rabbit infrastructure. No additional service is required.
3. Deploy Gateway checkpoint publication and the Web client generated from the Activity contract. Check the collector watermark and retry/DLQ depth during rollout. Missing tracking is shown as unavailable until a healthy collector watermark arrives.

The online repository excludes intervals older than a rolling 112-day (16-week) window. An hourly cleanup removes expired interval rows, clips crossing intervals at the cutoff, and deletes expired per-user observation metadata, independently of the Organization log's seven-day Timescale policy. The global tracking start remains to distinguish covered days from dates before instrumentation. Per-user metadata retains the last confirmed observation only inside the same 112-day window. Gateway rotates cumulative segments at most every 24 hours, so retained interval records are bounded. Query-time clipping enforces the window even between cleanup runs.

No production or existing local application database is migrated by the tests. `bun run --cwd apps/activity test:integration` provisions isolated PostgreSQL/Timescale containers and verifies migrations, persistence, union, DST, redelivery, retention and private HTTP identity binding. Rabbit consumer integration fakes only broker delivery; the online repository and database are real.

### Online world provenance

Deploy `drizzle/migrations/0003_online_world_provenance.sql` with the activity migration command before deploying the activity API, then deploy the gateway producer. Each online day returns `worlds` (sorted distinct worlds from positive confirmed intervals) and `worldsComplete`. Historical intervals and queued checkpoints from older gateways remain unattributed; a day that includes any such interval has `worldsComplete: false`. Never infer their world from a current character. Empty days return an empty list and complete provenance. Total online time still unions overlapping sessions across worlds, rather than adding their durations. The Rabbit checkpoint world is optional for rolling compatibility; new gateway segments persist their world in Redis and PostgreSQL. Changing world rotates the segment while retaining confirmed cumulative history.

An old gateway checkpoint may still extend an existing segment during rollback. If either cumulative version lacks a world, the stored segment is conservatively unattributed; a later retry cannot relabel that history. Checkpoints that attempt to change one known world to a different known world are rejected.
